A configuration-driven decision plane for MCP calls.

Aegis sits between the agent and the backend. Every tool, resource, prompt and completion call passes a fail-closed engine that applies identity, policy, scope, approval, egress, screening, output control and audit before reaching a real system.

  • One configuration file drives it; the governed project is untouched.

Independent project under Apache-2.0. It runs on its own or inside an Apache Knox topology.

Aegis Gateway 2.010 / 26

The governance model

Identity to audit, every call.

  • Identity required. JWT/JWKS, mTLS/SPIFFE, static or Knox subject.
  • No token passthrough. Backends get a scoped, gateway-issued credential.
  • Default deny. Only configured tools, classes, resources and destinations are reachable.
  • Separation of duties. Destructive calls need an independent approver and a receipt.
  • Catalog pinning. A changed tool is quarantined; a signed catalog decides what starts.
  • Egress control. URLs and DNS classified, redirects not followed, DNS pinned.
  • Output declassification. Redaction, structured allowlist, or handle-only.
  • Properties S1 to S31. Each names an enforcing class and a test that stays green.

Aegis Gateway 2.020 / 26

Adoption

Connect an AI IDE in minutes.

To the IDE, Aegis is a normal MCP server over HTTP. Point the client at the gateway URL and present a bearer token. Aegis decides the rest.

  • Kiro and Cursor: url plus Authorization: Bearer.
  • VS Code: a prompted secret input plus an http server entry.
  • Claude Desktop and the MCP Python SDK: the same URL and token.
  • Ready-made settings ship for 27 Apache projects, own host and Knox.

The token is the identity

Its groups decide which tool classes it may use, whether a write needs an approver, and what it may read. Issue a narrow token per person or agent.

Deploy on AWS, then swap the local URL for the load balancer address. Nothing else changes.
