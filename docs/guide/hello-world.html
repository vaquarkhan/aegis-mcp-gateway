Your IDE talks to Aegis. Aegis talks to the engine. The engine never sees the agent’s raw tool call until governance allows it.

HELLO WORLD

Add Aegis to your development cycle.

You do not rewrite Kafka, Spark, Airflow, or your existing MCP server. You put Aegis in front, point your IDE’s MCP settings at Aegis, and every tool call is classified, scoped, approved when needed, and audited before the backend runs.

WHAT CHANGES

One new hop. Same tools. Governed decisions.

Before

Cursor, VS Code, Kiro, or Claude Desktop talks straight to an MCP server or product API. Whatever credential that path holds can execute the tool.

After

The IDE talks only to Aegis (/mcp). Aegis applies tool class, groups, policy, egress, approval, dry-run receipt, and audit. Only then does it call your MCP server or Apache engine.

Aegis does not replace backend authorization or network policy. Use least-privilege backend credentials in every path.

PICK ONE START

Three Hello World paths. Same governance engine.

1. You already have an MCP server

Keep the server’s tools and schemas. Classify them in YAML. Aegis fronts them with no code change in that project.

2. You run an Apache engine with a shipped profile

FIRST-GREEN PATH

Hello World: build once, govern one project, prompt from your IDE.

Use this when you want your first green path. The Spark and Iceberg walkthrough is the fullest IDE story; the existing-MCP tutorial is the fastest if you already speak MCP.

Step 1 - Build Aegis

JDK 17+ and Maven 3.9+. From the repository root:

mvn -B -Preal-engines -DskipTests install

That produces aegis-gateway/target/aegis-gateway-2.0.0-SNAPSHOT-all.jar (and Spark/Kafka fat jars when those sources are needed).

Step 2 - Start a real backend and Aegis

Recorded existing-MCP scenario (two downstream MCP servers, both front doors, and assertions):

# PowerShell, from the repository root
.\examples\adopters\existing-mcp-server\setup.ps1 -Destination C:\aegis-engines
# Set AEGIS_MCP_PYTHON, AEGIS_NODE, and AEGIS_MCP_FILESYSTEM_JS to the paths printed above.
$env:AEGIS_KNOX_HOME = 'C:\knox\knox-3.0.0'   # only needed for the Knox door
.\examples\adopters\run-example.ps1 existing-mcp-server -Keep

# bash, from the repository root
examples/adopters/existing-mcp-server/setup.sh /opt/aegis-engines
# Export AEGIS_MCP_PYTHON, AEGIS_NODE, and AEGIS_MCP_FILESYSTEM_JS as printed above.
export AEGIS_KNOX_HOME=/opt/knox/knox-3.0.0     # only needed for the Knox door
examples/adopters/run-example.sh existing-mcp-server --keep

The setup scripts install pinned downstream servers outside the repository and print the three required paths. Set all three variables before running the example; without them the test is skipped, never passed. Omit AEGIS_KNOX_HOME only when you do not run the Knox door.

Or pick your Apache project name (kafka, airflow, spark-connect, …) from the tutorial index. Each tutorial lists the engine command, own-host YAML, and Knox flavor.

Manual own-host path (after the setup above):

# Copy the retained own-host configuration to a working file first.
cp examples/adopters/existing-mcp-server/aegis/own-host.yaml my-aegis.yaml
export AEGIS_SIGNING_KEY='replace-with-32-or-more-bytes-of-secret'
java -jar aegis-gateway/target/aegis-gateway-2.0.0-SNAPSHOT-all.jar \
  --config my-aegis.yaml

Do not use adopters/configurations/existing-mcp-server/existing-mcp-server.yaml directly as an own-host quick start. It is a shared deployment template without a host section and uses non-local backend settings. In your working copy of the retained own-host.yaml, replace run-specific stdio paths or source URLs, loopback egress settings, identity token environment names or digests, audit path, and signing key as needed. Start the configured downstream MCP server before Aegis. Unknown keys fail closed at startup.

Step 3 - Point the IDE at Aegis (not at the engine)

Ready-made files live under adopters/tutorials/<project>/ide/. Example for Cursor (own host):

{
  "mcpServers": {
    "aegis-existing-mcp-server": {
      "url": "http://127.0.0.1:8080/mcp",
      "headers": {
        "Authorization": "Bearer REPLACE_WITH_YOUR_TOKEN"
      }
    }
  }
}

The generated files name inputs or placeholders; they do not contain usable token values. Until Aegis is listening on that URL, the IDE shows an empty or failing MCP server; start the gateway first.

Step 4 - Send one prompt

Use a prompt the tutorial lists under “Prompts to try” (for example list jobs, list topics, list DAGs). Expect one of:

  • ALLOWED for a READ your group may call
  • APPROVAL_REQUIRED / deny for MUTATE / DESTRUCTIVE until an independent approver and (for destructive) a fresh dry-run receipt are in place
  • An audit line in the configured audit.file JSONL journal

DAY-TO-DAY WORKFLOW

How Aegis sits in an existing development cycle

1. LocalDeveloper runs engine + Aegis on loopback; IDE MCP points at 127.0.0.1:8080/mcp.
2. SharedTeam deploys one Aegis (own host or Knox) with reviewed YAML; CI can run contract tests and Keep profiles.
3. ChangeNew tools = YAML (or OpenAPI draft) + classification + resources + egress. No agent SDK rewrite.
4. EvidenceApprovals and denies land in the hash-chained audit journal; verify with --verify-audit.

What you keep doing

Write product code, operate Kafka/Spark/Airflow, use IDE agents for exploration and change requests. Backend APIs and MCP servers stay yours.

What you add once

One Aegis configuration per governed surface; host identity (JWT or static tokens); approver groups; egress allow list; IDE MCP entry that targets Aegis.

Container and cluster options: Dockerfile and Helm chart. Operator details: developer guide and configuration reference.

APACHE PROJECTS

How to put secure MCP in front of an Apache project

Aegis is built so the Apache project itself changes nothing: no new dependency, no fork, no rebuild. You choose the source type that matches the product’s real API.

Project has…Aegis sourceStart from
Its own MCP servertype: mcpexisting MCP server tutorial
A documented REST / HTTP Admin APItype: http declarative toolsShipped adapter under adopters/configurations/adapters/<name>/
SQL over JDBC (Hive, Calcite/Avatica, …)type: jdbcHive / Calcite profiles + JDBC converter
ZooKeeper data tree / AdminServerZooKeeper converter + HTTP Admin commandsZooKeeper tutorial
Spark Connecttyped Spark Connect pluginSpark Connect tutorial
Kafka Admin / Connect RESTkafka-admin + HTTP Connect toolsKafka tutorial

Operator checklist for a new Apache surface

  1. Find the closest profile in adopters/configurations (or generate an OpenAPI draft for a REST API).
  2. Classify every tool: READ, MUTATE, or DESTRUCTIVE. Unlisted tools default to DESTRUCTIVE (or use unlistedTools: HIDE).
  3. Name typed resources with JSON pointers (for example kafka:topic from /topic) so policy can constrain objects, not only tool names.
  4. Set egress.allowCidrs (or hosts) to the engine’s real addresses only.
  5. Wire groups: readers, operators, approvers. Separate people who request from people who approve.
  6. Run the matching tutorial Keep (or contract test) before you call the path “verified” for a release.

Twenty-six profiles already have retained own-host and Knox Keep runs with IDE tutorials. Six more (Atlas, Cassandra, Hive, Impala, Paimon, Ranger) are contract-supported until a full product stack Keep lands - see adopter status.
