THE PROBLEM

MCP makes tools easy to call. Governance decides whether a call may execute.

MCP is a common protocol for clients such as agents, IDEs, and services to discover and call structured tools. That turns a data platform, cluster, catalog, or business API into an agent-callable control plane. Route security can protect POST /mcp, but it cannot by itself decide whether a specific tool, resource, and argument set is appropriate.

Without semantic governance

A model can be influenced by untrusted content while a broad service credential can carry out its tool request. The backend and a route ACL see only part of that decision.

With Aegis

Aegis evaluates the tool class, typed resource, policy, egress, approval, receipt, and audit intent before it resolves the backend credential.

OPERATING MODEL

Aegis owns one MCP decision path; hosts are deployment choices.

Aegis owns the MCP action decision in every deployment. Its own host establishes identity with Aegis configuration. An optional Knox integration supplies external identity and route admission from an existing topology. The Aegis engine then evaluates exposure, input and resource scope, policy, egress, rate/budget, breaker, screening, approval, receipt, audit intent, and execution in a fixed order.

READStandard governance controls.
MUTATEIndependent per-call approval by default.
DESTRUCTIVEApproval plus a fresh bound dry-run receipt.

Aegis complements backend authorization and network policy; it does not replace either. Use least-privilege backend credentials regardless of tool class.

THREAT COVERAGE

OWASP MCP Top 10: coverage is not a claim of elimination.

The OWASP MCP Top 10 is a threat checklist for systems that expose AI-callable tools. Aegis maps each item to a gateway control and states what remains an operator, identity-provider, backend, or network responsibility. See the product threat model and security validation record for STRIDE scenarios and dated control-suite results with their attestation status.

MCP01 to MCP03Strong gateway controls for tokens, privilege scope, and changed tool definitions; provided the first pin is trusted.
MCP04 and MCP05Partial supply-chain and command-execution coverage; release controls and runtime sandboxing remain outside Aegis.
MCP06Prompt-injection screening reduces impact but is heuristic. Typed scope and independent approval are the durable safeguards.
MCP07 and MCP08Strong authentication/authorization and local audit evidence controls; identity operations and off-host monitoring remain deployment work.
MCP09Shadow servers cannot be discovered or prevented by a gateway that is not in their network path.
MCP10Caller-filtered discovery and guarded content help, but clients can retain or disclose received data.

Read the full S1 to S31 security mapping, test evidence, and residual responsibilities. The HTML security guide collects the threat-model diagram, abuse cases, and validation record in one place: open the security guide.

DEPLOYMENT ONE

Run Aegis as its own host.

Use the shaded executable for an HTTP(S) or stdio MCP endpoint, or the container image and Helm chart built from the repository (Dockerfile, charts/aegis). Configure host identity, routes, sources, policy, audit, and state explicitly.

java -jar aegis-gateway/target/aegis-gateway-2.0.0-SNAPSHOT-all.jar --config aegis.yaml

Open the configuration reference for TLS, JWT/static identity, OAuth metadata, CORS, route and per-tool scopes (actionScopes), egress, the signed serverCatalog with break-glass containment, and source settings. Use the fixed-journal audit verification endpoint only through its dedicated verifier group.

DEPLOYMENT TWO

Optional: run Aegis in Apache Knox 3.0.

Use this integration only when Knox already supplies your HTTP perimeter. Knox owns edge authentication, identity assertion, and route admission. Aegis receives the Knox subject, parses the MCP body, and applies its standard per-tool governance decision.

  1. Build Aegis with JDK 17+ and Maven 3.9+.
  2. Copy the documented jars or the Knox bundle to Knox ext/.
  3. Add AEGIS_MCP to a topology with identity assertion and authorization.
  4. Point the service at the Aegis configuration and restart Knox.

Follow the exact Knox installation steps. Add only the state and plugin jars required by your configuration.

OPERATIONAL CHECKLIST

Operate safely from day one.

  • Keep backend credentials least-privileged and outside configuration files; where the backend should see each user, use RFC 8693 token exchange (credentials.type: token-exchange).
  • Start custom controls from the reference PII, secrets and change-window hook services in adopters/hooks.
  • Allow only known backend egress destinations and enforce network policy below Aegis.
  • Separate approvers from requesters; delegated callers cannot approve.
  • Protect audit journals and durable state as operational records.
  • Validate the exact backend version and front door you will run.
  • Read documented limitations before treating a control as a complete defence.
