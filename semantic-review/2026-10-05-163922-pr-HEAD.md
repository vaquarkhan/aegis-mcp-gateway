# Threat-model evidence and governance controls

The orphan branch introduces a threat model, a security-validation catalogue, and a claims-matrix row that present the governance engine as a fail-closed boundary. The review therefore used the branch’s five-commit first-parent sequence rather than a merge-base diff: `b8ad994` is the root import, `ef35ec0` adds the threat-model/evidence material, and subsequent commits change adopter/documentation counts. The egress implementation checks declared targets and nested HTTP(S) URLs before execution, rejects disallowed schemes, user info, non-allowlisted hosts, and each initial DNS answer; redirect following is separately disabled for the MCP HTTP client. The threat model also correctly identifies DNS check/connect rebinding and plugin-owned sockets as residual/external controls rather than claiming end-to-end network confinement. **Watch for:** **confirmed** the matcher advertised as linear can be driven to quadratic work by a sufficiently long configured glob and attacker-controlled resource; **confirmed** the new `verified-current` security evidence cannot be tied to the reviewed HEAD or a retained execution artifact.

**Verdict**: NEEDS_CHANGES

## High-level view

The governance chain places egress before approval, credentials, and execution, so an HTTP(S) destination rejected during target discovery does not reach the backend. **Confirmed:** this is a pre-connect DNS decision, not a socket-level pin; the documented DNS-rebinding and non-HTTP-plugin residuals must remain operational release conditions.

Authorization, resource scope, policy, and hooks all use the same wildcard matcher. **Confirmed:** its single-star fallback restarts a growing literal suffix after each input-character fallback, so a long configuration pattern and a caller-supplied resource can consume quadratic CPU in the decision path.

The new threat-model record gives scenario-to-test citations and appropriately scopes several non-claims. **Confirmed:** its release-evidence assertion is not auditable on this branch because the record names a different working branch, omits a commit/tree ID and preserved Surefire output, while the claims matrix labels the result `verified-current` and itself requires raw output or a transcript before that promotion.

## Wildcard policy matching can amplify a caller-controlled resource

**Confirmed.** `Glob.matches` records only the most recent `*` and, after a mismatch, resets the pattern index to the character immediately after that star while advancing the input one character (`aegis-engine/src/main/java/io/github/vaquarkhan/aegis/engine/control/Glob.java:23-45`). For a pattern shaped as `*` followed by a long run of `a` characters and a terminating `b`, evaluated against a sufficiently long run of `a` characters, each fallback rechecks nearly the whole literal run. If both pattern and resource lengths grow together, the work is O(pattern-length × resource-length), not linear.

This matcher is on the authorization path, not merely a presentation helper: `ScopeRule` matches caller-controlled extracted resources; `RulePolicy` matches tools and resources; `ContentGovernor` filters and authorizes URIs; and `ProjectGovernanceGuardrail` applies protected-resource patterns. The existing test, `ControlsTest.globIsLinearAndCorrect` (`aegis-engine/src/test/java/io/github/vaquarkhan/aegis/engine/control/ControlsTest.java:168-176`), fixes the pattern at six `a*` fragments and only checks one 5,000-character input against a two-second wall-clock threshold. It cannot detect the two-dimensional growth and makes the security-validation catalogue’s control-to-test assertion misleading for this property.

The control should either use a matcher with a proved linear bound for these wildcard semantics or bound both operator pattern complexity and untrusted resource/URI length before evaluation. The remediation test needs to vary both dimensions and assert a complexity/limit contract rather than a machine-dependent elapsed time.

## Security-validation status has no immutable source or run provenance

**Confirmed.** The threat-model addition says the focused suite was revalidated “on this tree” and its claims matrix G03 reports 227 selected tests with `verified-current` status (`docs/THREAT-MODEL.md:20-21, 344-363`; `docs/evidence/CLAIMS-MATRIX.md:111`). The companion evidence record instead identifies the test subject only as the working branch `aegis-2.0-feature-brach-for-review-10052026` (`docs/evidence/SECURITY-VALIDATION.md:38-43`), which is not the reviewed `consolidate-into-threat-model-review` HEAD `b7ed14acc08d4cfb244238055bd30bb9fdf082d6`. It supplies prose totals and a command, but no commit/tree digest, raw Maven/Surefire report, report hash, or reference to a retained output artifact.

This conflicts with the matrix’s own status definition — `verified-current` means this working tree ran the named command — and its change rule requiring command output or a raw transcript under `docs/evidence/` before promotion (`docs/evidence/CLAIMS-MATRIX.md:28-29, 78-81`). The five-commit sequence compounds the gap: the branch is rooted by the broad `b8ad994` import, the security record is added in `ef35ec0`, and later commits amend validation/adopter documentation through `b7ed14a`. Git metadata can show a human author and the `ef35ec0` `Generated-by: Cursor` disclosure, but it cannot establish the stated independent review or reproduce which imported source snapshot produced the 227-test total.

Bind the result to the tested source revision and retain the raw run output. Until that is done, release governance should not use G03 as a `verified-current` attestation for this HEAD. The scenario-to-test mapping remains useful as a test plan, but it is not evidence provenance.

## Egress boundary is explicit but pre-connect

The threat model’s egress claim is materially narrower than a full outbound-network guarantee. `GovernanceEngine` gathers executor-declared targets plus URLs found in arguments and round-trip input responses, checks each through `EgressGuard`, and denies before rate, approval, credential lookup, and executor invocation (`aegis-engine/src/main/java/io/github/vaquarkhan/aegis/engine/GovernanceEngine.java:260-280`). `EgressGuard` normalizes allowlisted hosts, rejects user-info, resolves all initial answers, and denies every non-public answer outside an explicit CIDR (`aegis-engine/src/main/java/io/github/vaquarkhan/aegis/engine/control/EgressGuard.java:43-108`). The cited focused tests exercise private/link-local answers, CIDR override, embedded/nested URLs, and redirect refusal (`ControlsTest:43-68, 119-123`; `GovernanceEngineTest:228-235`; `ExistingMcpServerProxyTest:147-159`).

The implementation itself documents the remaining DNS re-resolution interval between `check` and the executor connection, and the threat model correctly leaves non-HTTP plugin sockets to network policy (`EgressGuard.java:31-34`; `docs/THREAT-MODEL.md:281-282, 325-330`). No additional finding is raised for those residuals because the new threat model explicitly identifies them; releasing with an unqualified claim that all backend egress is enforced would nevertheless be inaccurate.
